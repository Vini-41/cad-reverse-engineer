# Coding standards

Judgement calls for `/code-review`. Mechanical rules live in `scripts/check`, which CI runs, not here.

- **Glossary vocabulary.** Rule names, finding messages, report text, docstrings and the shipped docs use the terms in `GLOSSARY.md` as defined there, and none of their `_Avoid_` words: a check *evaluates* the built solids, and *source* names a document.
- **One status authority.** The status (NOT VERIFIED, PARTIAL, VERIFIED PENDING REVIEW, VERIFIED, exact) is computed in one place; every other module that prints or writes it reads that result.
- **A rule is documented once.** A new or changed rule updates the one reference doc that owns its format; `SKILL.md` points to it rather than restating it. That update belongs to every ticket that changes a rule, whether or not the ticket names the doc, so it is never scope creep. Shipped docs follow `/writing-for-agents`: a line describing how the tool behaves "today" is sediment, and how a rule works inside is exposition unless the agent needs it to meet the rule.
- **Facts about a check kind sit in `CHECK_KINDS`.** Its quantity and tolerance key live in that table in `project.py`. `run_checks` in `geometry.py` dispatches on `kind` to evaluate, and that is the one place a branch on a kind belongs.
- **A departure from the spec is recorded on the spec.** Where the diff departs from its spec's Implementation Decisions, the spec issue carries a comment saying what changed and why.
- **Every promised behaviour has a test.** Each line of the brief's Desired behavior is shown by a test in the diff, or by an existing one the close-out names, whether or not a criterion asks for it; a line no test shows is a Spec finding.
- **A bug's repro runs on the fix.** The brief's Current-behavior scenario, re-run on the diff, shows each Desired-behavior line it reaches. A test fixture changed so the scenario's failure no longer occurs (a value supplied so the model builds) does not stand in for it; a line the scenario contradicts is a Spec finding.
- **A finding, never a traceback.** Every path that reads project input or user code (YAML, `model.py`, `build()`'s return, source files) turns failure into a named finding, caught where the input enters and as narrowly as the library allows. New damage it handles gets a case in the test suite's `DAMAGE` table. `schema.py` drops a project-file key of the wrong type before any other module reads it, so a claimed traceback is shown by a `DAMAGE` row that goes red, not by reading the code.
- **A command leaves the project loading.** A command that edits a project file (`cadrev source`, `cadrev init`) is tested by running it and then loading the project: no `[yaml-syntax]`, and the edit is in the loaded value. A `DAMAGE` row shows only that no traceback escapes, so it does not stand in for this test.
- **A finding hides only what it explains.** A new finding that stands in for an existing one (`[number-ambiguous]` for `[value-not-in-quote]`) does so only for the values it names; every other value in the item is still checked, and a test shows a wrong value beside it is still reported.
- **Near misses.** A rule that refuses input is tested beside its near miss, the closest input it must accept: `Fig. 2` refuses 2, `a section 4 mm thick` keeps 4. A new quote form the reader handles gets a row in the test suite's `QUOTES` table. A reader that accepts a new form is also tested against its look-alikes: inputs that begin with the form but mean something else (`twenty-first`, `one hundred`, `two-thirds` beside `twenty`, `one`, `two`; `id: "paper  # main"` beside `id: paper  # main`). A test that already passes before the fix (the near miss, or a criterion that already holds) is a guard, named `test_guard_…`. A test that a new rule is absent first shows it present, so it goes red before the rule exists; `scripts/red-on-main` shows which tests are which. What a brief says stays unchanged is tested at the edge of the inputs it covers, beside the change that could break it (a long title on a narrow figure).
